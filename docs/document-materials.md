# PDF and PPTX material contract

PDF/PPTX viewing is a separate material flow from worksheet preparation. Worksheet import may rasterize and interpret pages and keeps its source provenance teacher-only. Document material upload preserves a static visible document for direct browser reading and never exposes worksheet provenance through document endpoints.

`POST /materials/{materialId}/assets/documents` accepts multipart PDF or PPTX with `Idempotency-Key`. The same key and bytes return the same upload; the same key with different bytes returns `409 MATERIAL_DOCUMENT_IDEMPOTENCY_CONFLICT`. `GET /materials/{materialId}/assets/document-uploads/{uploadId}` returns the recoverable status. A ready result contains an immutable display asset, revision and ordered page manifest. Source assets are excluded from normal asset lists and learner reads.

Uploading during a lesson uses the same private-draft material flow as the library. A ready document is added to the teacher's material selector while the current lesson material remains active. The teacher must explicitly assign the ready material through the existing lesson-material assignment contract.

Document upload errors and recovery instructions remain visible and keyboard-focusable in the open lesson activity panel, including narrow screens. When the panel is closed, the message remains available in the lesson workspace.

On narrow screens the activity panel is not clipped by the lesson workspace: teachers can scroll to its labels, fields and actions, with room for the bottom device safe area.

On narrow screens the open activity panel behaves as a labelled modal: keyboard focus enters the panel, Tab stays within it, and Escape closes it and restores the previous focus. An open child menu handles Escape first. The panel is not modal on desktop and is suspended while the whiteboard, a covered library game, or external-activity focus hides it.

Validation limits are 64 MiB, 50 visible pages/slides, 10,000 PPTX ZIP entries and 256 MiB expanded PPTX content. PDF display bytes remove actions, forms, embedded files, JavaScript and annotations. PPTX display bytes reject external relationships and active/OLE/executable/media payloads and remove hidden slides, notes and comments. Visible content, including visible answer keys, is intentionally shared.

The standard internal PowerPoint `printerSettings` part is accepted only with the matching presentation relationship and content type, and is removed from the display derivative. Other binary parts remain rejected. Package relationship and content-type namespaces are normalized for the static viewer without changing their namespace meaning.

Material asset content requires the existing per-request material or teacher-source authorization and is returned with `Cache-Control: no-store`. Browser asset readers use `cache: no-store` and the non-secret `access=private-v1` URL identity; the old URL remains supported. Previously cached old-URL responses can remain reusable until their former ten-minute freshness expires, and a rollback to the former policy restores that risk. A new response cannot erase copies already stored by a user.

Material blocks use `type=document`, `documentAssetId`, `documentFormat`, `documentRevision`, ordered `documentPages`, `documentPdfLayout` and `documentPdfSeparateCover`. Existing schema v1/v2 readers remain valid. The browser loads `react-pdf` or `pptx-react-viewer` lazily from the application bundle; PDF.js worker, CMaps, fonts and WASM are served from the application origin. The `.mjs` PDF.js worker must be served with a JavaScript MIME type so the browser can import it as a module.

The teacher publishes document focus, revision, page/spread and placement through an authorized command on the existing lesson viewport. The API token carries a fail-closed viewport publication claim; collaboration-service assigns the canonical revision, persists accepted state in the Yjs snapshot and rejects learner commands or direct learner Yjs mutations of `materialViewport`. Learner cursor, answer and permitted annotation updates remain writable. Zoom and pan remain local. Annotation anchors include block, immutable revision and page identity. Panel/expanded switches retain viewer state, and only one focused primary activity occupies the workspace.

New PPTX annotations use slide-relative coordinates, so their position follows the slide across local zoom, pan and viewport sizes. Existing annotations keep their original stage-relative coordinates and remain available; their original slide-relative position cannot be reconstructed when the author's viewport was not recorded. Both use the existing page anchor and schema. Older open clients continue to display exchanged elements with their earlier stage-relative placement; reload those clients for accurate placement of newly created slide-relative annotations.

The eraser resolves each stroke against its own coordinate space. A live erase is a separate undo step from the preceding gesture, including when the actions are close together.

On screens up to 640 CSS pixels wide, initial entry and a teacher-controlled PPTX slide change keep the start of the selected slide stage in view even when the teacher's normalized scroll position would place it above the learner's viewport. A later deliberate scroll continues to use the existing shared viewport synchronization. Desktop behavior and document authority do not change.

The library reader and the teacher's standalone play preview permit local PDF page and spread navigation. They do not publish lesson viewport commands. A learner in a shared lesson still follows the teacher-controlled viewport.

In PARALLEL, each assigned student and the authorized teacher share an individual lesson/student/material Yjs document; group material rooms cannot be opened as a substitute. Legacy lesson/material annotations without a reliable author remain untouched and are shown only to an authorized teacher in a separate read-only unallocated view. Historical material annotations remain discoverable from the lesson card after assignments are removed. The original material and its assets retain their independent access checks; if unavailable, annotation regions are displayed separately without the background. A mixed older-tab snapshot containing historical identifiers is retained without student attribution in the teacher-only archive, and those identifiers are removed from the student's layer. Unknown shapes are retained as unallocated instead of being guessed.

Legacy per-student REST annotations and the new Yjs room remain separate stores. The teacher can inspect the selected student's legacy layer as a separate, automatically refreshed read-only view, and the student is asked to reload the older lesson tab for shared drawing; this does not claim automatic migration or synchronization. Rollout and rollback must account for already-open clients. Material collaboration access is revalidated on admission and periodically for live sockets; a policy failure closes the connection. Parallel drafts survive focus changes in memory in the same tab. The client clears its unsaved indication only when the server acknowledges a snapshot covering the local state; while pending, leaving or signing out warns the user and the browser receives a before-unload guard. Drafts are not stored unencrypted in the browser and can still be lost on forced reload or crash.

Document collaboration reuses the existing authenticated Yjs `/collab/ws` connection and does not open a document-specific WebSocket, WebRTC connection or TURN allocation. For the approved `.ru` route that socket therefore follows the existing Selectel `rf-two-hop` policy. Any future separate realtime channel for documents must be added to the same server-authored Selectel route contract before it can be enabled; it must not select an edge endpoint in the browser or bypass the collaboration route.
