# Lesson whiteboard contract

The feature is guarded by gateway `playsay.whiteboard.enabled` (default `false`). Local implementation does not imply rollout. Delivery, schema convergence, backups and recovery remain governed by the infra runbook.

## Identity, scope and access

One stable board belongs to each scheduled lesson context: `GROUP` for SHARED, or a roster student's UUID for PARALLEL. It has no material dependency and is not an assignable material. Creating/opening is idempotent under the lesson lock. Replacing the lesson material does not replace the board. PARALLEL managers must explicitly select a roster student; learners can only resolve their own context. Current roster, assigned teacher/delegation/admin authority, deletion intent, admission and server-authoritative lesson deadline govern live access. History uses a separate roster/management read policy and does not issue write tokens after completion.

`lesson_whiteboard` stores background, learner permission, active surface, control revision and content epoch. A collaboration document has exactly one binding: ordinary material, `LESSON_GAME` with a GROUP game launch, or `LESSON_WHITEBOARD` without a material/game launch. The additive migration extends the existing game-binding constraint; it does not edit the applied game migration. Lesson/student/document foreign keys and the unique `(lesson_id, context_key)` constraint preserve lifecycle and context identity.

## HTTP and notification

Public wire schemas are in `contracts/openapi.yaml`; frontend clients are generated by the existing export/generation tasks.

| Endpoint | Behavior |
| --- | --- |
| GET `/schedule/lessons/{lessonId}/whiteboard?studentSubject=…` | Feature availability, manager authority and current authorized context, including nullable board |
| POST same path | Active manager ensures and presents that context, including a lesson without material |
| GET `/schedule/lessons/{lessonId}/whiteboards` | Authorized history summaries, without snapshots |
| GET `/schedule/lessons/{lessonId}/whiteboards/{boardId}` | Authorized current durable snapshot; history remains readable after the live deadline |
| PUT same board path | Active manager command with `expectedRevision`, optional background, learner permission, surface and confirmed clear |

Stale control revisions receive HTTP 409; clients refresh canonical state and retain a visible recoverable error. Background accepts a six-digit hex color independently of the app theme. Learners cannot send control commands. `lesson.whiteboard.changed` travels over existing lesson realtime, carries only lesson ID, and filters an individual notification to its learner and managers. Clients reread authoritative context; a newer control revision wins over a delayed older response. Poll/online/foreground recovery also works without an attached material socket.

## Collaboration protocol

Boards use the existing server-authored collaboration token and `/collab/ws` route, with signed `documentKind=LESSON_WHITEBOARD`, board ID, epoch and null material. Room name is `lesson:{lessonId}:whiteboard:{boardId}:epoch:{epoch}`. There is no second provider, media connection or TURN allocation. Existing material names and channels are unchanged.

| Type | Envelope |
| --- | --- |
| 0, 1 | Existing Yjs sync and awareness |
| 4 | Existing negotiated version-1 liveness hello/probe/ack, without probing a server that has not advertised support |
| 5 | Length-prefixed JSON: server `{type:"hello",version:1,whiteboard:true}`; teacher `{type:"camera",version:1,sourceClientId,region:{x,y,width,height}}` |
| 6 | Server durable acknowledgement `{type:"persisted",version:1,contentEpoch,stateVector,deleteSet}`; vector is base64-encoded Yjs state vector |

Passive board sessions also recheck policy every five seconds and close on failure; mutation authorization is checked for each frame. Every board frame is serialized in its room and rechecks trusted gateway policy before mutation. The service-token-only `/internal/whiteboards/{documentId}/policy` binds current subject, roster/admission/lifecycle and epoch. Disabled learner ink permits synchronization and viewing, but no changed content. Candidate Yjs state is validated before apply, including deferred structs/deletions, root names, immutable ownership, teacher-only camera, element schema and content bounds. A learner can change/delete only their own elements. Raw control-map changes and public snapshot writes are rejected. A connection-owned awareness client ID and manager authority are required for camera commands.

The only document roots are `annotations` and server-authored `whiteboardCamera`. Per-element maps use `ownerSubject`; text uses Y.Text and stroke points append to Y.Array. Geometry patches preserve concurrent text/style. Undo tracks local origins and does not undo another actor's independent contribution. Whiteboard world coordinates are independent of material-page coordinates. Positions are bounded to ±100000, zoom to 25–400%; teacher publishes a world region, learners fit it to their aspect ratio and may locally pan before returning to the teacher.

## Persistence, clear and resources

A snapshot uses `schemaVersion=1`, `encoding=yjs-update-v1`, `coordinateSpace=whiteboard-world`, content epoch, base64 update, state vector and canonical delete-set update. Deletion acknowledgements are compared separately because a Yjs state vector does not advance on deletion. Only trusted service writes persist it. "Saved" means an actual durable response whose vector covers current local state, including deletes; server receipt alone is insufficient. Failed loads are explicit errors, not empty saved boards. Existing bounded immutable snapshot retention/retry is reused. Closing the last board socket requests a drain; trusted already-accepted snapshots may drain after lesson completion, while new client writes/tokens are denied. History shows the last durable state. Process loss before a durable acknowledgement is outside the save guarantee.

Clear keeps board ID, background and permission but advances epoch and rotates the collaboration document ID/room. The former persistence target is deleted. Delayed old saves receive 404, old tokens fail policy, and old undo/cursors are not seeded into the new epoch. Cancellation sends no command.

Current limits are the stricter existing snapshot limit of 1,000,000 serialized bytes, 10000 elements, 200000 stroke points and 20000 characters per text element (the shared editor may impose a smaller input limit). Existing frame/backpressure limits remain. The browser reserves headroom below the server snapshot ceiling, rejects oversized/out-of-world edits locally and keeps prior drawings and undo available. Pending board input is bounded to 100 messages / 2 MiB per room. Browser cache holds at most 16 unsaved contexts, reclaims inactive saved state and never silently evicts pending edits. A new context beyond that budget shows an error. Confirmed clear may discard the explicitly cleared epoch.

Switching surface retains inactive local Yjs state and pending edits, suspends its sockets and game/external input, and preserves material page/answers/annotations and the LiveKit owner. It sends no shared game stop. The board selector remains reachable while a library game covers the material; board presentation suspends and hides that same game stage, retaining its iframe until normal connection recovery. Returning restores the existing launch. Late presentation callbacks do not override the visible board. Drawing supports mouse/touch/pen, two-finger pan/zoom, keyboard camera movement, focus-bound editing, local expand and an addressed clear dialog. History uses the same renderer with drawing/control/credentials disabled.

## Verification and compatibility boundary

Implementation evidence belongs to the OpenSpec change and local test reports. The owner requires rollout outside lessons. Enable the default-off flag only after aligned gateway/collaboration/frontend rollout and refreshed-client checks before the next lesson. Presentation into an already running legacy lesson is unsupported; no legacy-tab blocker is added. A new client waits for version-1 board hello and shows a reload state without drawing if capability negotiation times out. No claim of real media, physical touch/stylus, production data migration or deployment acceptance follows from synthetic local browser checks.
